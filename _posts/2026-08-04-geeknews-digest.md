### 3. JSON은 당신을 속이고 있다 (1pts)
**요약**: 이 글은 `JSON.parse(JSON.stringify(value))`가 JavaScript 상태를 완전하게 복사하는 방법이 아니라고 정면으로 말합니다. `undefined`, `Function`, `Symbol`, `BigInt`, `Date`, `NaN`, 순환 참조는 JSON의 표현 범위를 넘어가거나 조용히 변형됩니다. 그래서 눈으로는 “복사했다”고 느껴도 실제로는 정보가 빠지거나 형태가 바뀝니다. 특히 상태 스냅샷, 메시지 전달, 로그 직렬화에서 이 차이는 치명적일 수 있습니다. 글의 핵심은 JSON을 범용 복제 도구로 착각하지 말라는 것입니다.
**기술적 배경**: JSON은 원래 교환용 포맷이지 자바스크립트 객체 그래프 보존용 포맷이 아닙니다. 객체의 프로토타입, 내장 컬렉션, 타입 정보, 순환 구조를 그대로 담지 못하는 이유가 바로 여기에 있습니다. 그래서 현대 JavaScript에서는 `structuredClone()`이나 명시적인 직렬화 규칙이 더 안전한 선택이 됩니다. 상태가 복잡할수록 “간단해 보이는 편법”의 대가가 커집니다.
**영향 분석**: 개발자에게는 디버깅과 상태 관리에서 가장 흔한 함정 하나를 다시 상기시킵니다. 스타트업에는 데이터 동기화와 캐시 복제에서 조용한 데이터 손실이 얼마나 비싼지 경고합니다. 인디 빌더에게는 토큰/세션/설정값을 JSON으로 막 덮어 쓰는 습관을 끊으라는 뜻입니다. OpenClaw는 스냅샷, 세션, 메모리 구조를 JSON 중심으로만 다루면 나중에 반드시 삐끗합니다.
**Master 액션 포인트**:
- OpenClaw에서 `JSON.parse(JSON.stringify(...))` 사용 지점을 찾아 `structuredClone()` 또는 전용 직렬화기로 바꿀 것
- eastsea.xyz의 상태 저장과 발행 메타데이터는 JSON 호환 여부를 명시하고, 손실 가능한 타입을 문서화할 것

**영향 분석**: 개발자에게는 사고 대응 문서도 코드처럼 버전 관리해야 한다는 교훈을 줍니다. 스타트업에는 장애 공지나 데이터 유출 공지가 늦어질수록 신뢰 손실이 커진다는 점을 환기합니다. 인디 빌더에게는 문제를 숨기느니 기록을 남기는 편이 훨씬 싸다는 뜻입니다. eastsea.xyz와 OpenClaw도 운영 변경 공지를 반드시 타임라인으로 남겨야 합니다.

### 14. 매니저가 된다는 것의 진실 (56pts)
**요약**: 이 글은 엔지니어에서 매니저로 넘어갈 때 대부분의 사람이 느끼는 고립감과 책임 변화를 아주 직접적으로 설명합니다. 매니저는 더 이상 자기 코드만 잘 쓰면 되는 사람이 아니라, 어려운 결정과 갈등 조정, 기밀 유지, 메시지 번역을 맡는 사람입니다. 그래서 하루를 마쳐도 “내가 오늘 뭘 했지”라는 감각이 약해질 수 있습니다. 저자는 이 역할이 기술적 승진이 아니라 다른 종류의 압박을 받아들이는 자리라고 말합니다. 결국 매니저는 일 잘하는 사람보다, 조직의 불안을 견디는 사람에 가깝습니다.
**기술적 배경**: 많은 조직이 매니저를 관리 업무와 사람 업무의 단순 합으로 봅니다. 하지만 실제로는 권한보다 모호성이 더 크게 늘어납니다. 피드백, 법적 책임, 인사 판단, 상향 보고가 동시에 들어오면서 기술자일 때와 전혀 다른 근육을 써야 합니다. 이 차이를 모르면 승진이 곧 착각이 됩니다.
**영향 분석**: 개발자에게는 관리자가 “일을 안 하는 사람”처럼 보이는 착시를 줄여 줍니다. 스타트업에는 리더십 부재가 성과 저하가 아니라 관계 붕괴로 이어진다는 경고입니다. 인디 빌더도 결국 사람을 붙이는 순간 이 역할 비용을 같이 떠안게 됩니다. OpenClaw 내부에서도 리더 역할은 코드 기여와 사람 관리로 분리해 기록해야 합니다.
**Master 액션 포인트**:
- OpenClaw의 리더 역할 설명서에 기술 책임과 사람 책임을 분리해서 적을 것
- 팀 확장 전에 의사결정 로그와 갈등 조정 로그를 남겨, 매니저 부담을 구조화할 것
- 원문: [The truth about being a manager](https://sofiakodar.github.io/posts/becomingmanager/)

### 15. 개발 도구가 오픈소스여야 하는 이유 (1pts)
**요약**: 이 글은 개발 도구가 왜 오픈소스여야 하는지를 에이전트 시대의 관점에서 다시 설명합니다. 코딩 에이전트가 소스 수정, 상위 저장소 동기화, 유지보수까지 자동화할수록, 도구 자체를 수정할 수 있어야 하는 이유가 커집니다. 글은 Devtools가 열린 상태여야 사용자가 프롬프트나 스킬을 곧바로 바꿔 자기 작업 방식에 맞출 수 있다고 봅니다. 즉 도구를 닫아 두는 순간, 사용자는 AI를 붙여도 완전히 자기 것으로 만들 수 없습니다. 개발 도구의 오픈소스화는 이상주의가 아니라 수정 가능성의 문제입니다.
**기술적 배경**: AI 도구가 강해질수록 사용자는 UI보다 행동을 바꾸고 싶어집니다. 이때 소스가 열려 있으면 프롬프트, 스킬, 확장 지점을 직접 손볼 수 있습니다. 반대로 닫힌 도구는 편하더라도 변형 비용이 커집니다. 에이전트 시대에는 수정 가능성이 곧 경쟁력입니다.
**영향 분석**: 개발자에게는 도구의 소스가 보이지 않으면 결국 제한된 자동화만 쓰게 된다는 경고입니다. 스타트업에게는 내부 개발 도구를 닫아둘수록 사용자의 실제 효율이 제한될 수 있다는 뜻입니다. 인디 빌더에게는 자기 도구를 스스로 고칠 수 있어야 장기적으로 빠릅니다. OpenClaw와 eastsea.xyz는 이 철학을 매우 직접적으로 닮아야 합니다.
**Master 액션 포인트**:
- OpenClaw의 내부 자동화 도구는 수정 가능한 스킬/프롬프트 계층을 기본으로 둘 것
- eastsea.xyz 운영 도구는 사용자와 운영자가 같은 방식으로 바꿀 수 있는 구조를 유지할 것
- 원문: [Devtools must be open source](https://blog.exe.dev/devtools-must-be-open-source)
