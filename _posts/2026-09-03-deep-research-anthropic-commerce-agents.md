# 카트에 환각은 담기지 않는다 — Anthropic 커머스 에이전트 블루프린트 완전 해부

> 2026년 9월 2일, 홀리데이 시즌을 앞두고 Anthropic은 소매·여행·통신·티켓 플랫폼용 **쇼핑 에이전트와 판매자(머천트) 에이전트**의 완전한 참조 구현을 공개했다. 발표문이 주목받은 것은 "장바구니 35% 증가, 구매 완료율 60% 상승" 같은 숫자 때문이지만, 이 글은 다른 것을 보려 한다. 저장소의 `docs/safety.md`를 줄 단위로 읽어보면 이 블루프린트의 진짜 주장은 하나다 — **에이전트의 신뢰는 프롬프트가 아니라 도구 호출 안쪽의 코드가 지킨다.** 카탈로그가 반환한 적 없는 상품은 장바구니에 담길 수 없고, 채팅창에 입력된 승인은 아무것도 승인하지 않으며, 결제 URL은 모델의 눈을 한 번도 거치지 않는다. 무엇이 어떤 계층에서 강제되고, 무엇이 여전히 모델의 언어 능력에 맡겨져 있는지 — 그 사다리의 전체 지도를 이 글에서 다룬다.

## Executive Summary

1. **핵심 기술 주장은 "신뢰의 계층화"다.** Anthropic은 에이전트 안전 규칙을 네 층으로 나눴다 — 도구 호출 안쪽에서 코드가 강제하는 규칙(fencing, provenance 게이트, 상한선, 승인 게이트), 런타임이 소유하는 규칙(grounding, 분석 예산, 메모리 추출), 프롬프트가 모델에게 요청하는 규칙, 그리고 배포자만 책임질 수 있는 규칙(인증, 결제, 개인정보). 같은 규칙이 세 가지 실행 경로(Messages API / Agent SDK / Managed Agents) 모두에서 성립하는 이유는 도구 실행이 단일 executor(`commerce_common/execution.py`)를 통과하기 때문이다.
2. **환각 상품은 구조적으로 차단된다.** 장바구니 쓰기는 "이 세션에서 카탈로그·주문 도구가 반환한 상품 id, 또는 이미 카트에 있는 라인"만 받는다. UI 표시용 페이로드도 서버 레코드와 조인(join)되고, 출처가 없는 id는 버려진 뒤 보고된다. 가격·약관 같은 고지문(disclosure)은 서버가 작성하고 모델은 상품을 지목하기만 한다. **모델이 지어낸 숫자는 화면에 도달할 경로 자체가 없다.**
3. **결제와 승인은 모델 밖에 있다.** 어떤 코드도 주문을 넣거나 카드를 긁지 않는다. `checkout`은 호스트가 완성할 장바구니를 렌더링할 뿐이고, 호스팅 결제 URL은 `checkout_handoff`가 모델을 거치지 않고 전달한다. 판매자 에이전트의 모든 쓰기는 '스테이징'이고, **"채팅에 입력된 승인은 아무것도 설정하지 않는다(an approval typed in chat sets nothing)"** — 승인은 포털의 승인 라우트나 SDK의 `host_approve`만 가능하다.
4. **숫자는 인상적이지만 자가 보고다.** 장바구니 최대 +35%, 구매 완료 가능성 +60%, 구축 시간 수일→수시간. Wix 엔지니어는 15분 만에 프롬프트를 받는 에이전트를 실행했고, Zomato 팀은 문서만 따라 무장애 실행, 또 다른 팀은 두 에이전트를 로컬에서 1시간 이내 구동했다. 단, 방법론·표본이 공개되지 않은 벤더 발표 수치라는 한계는 명시해둔다.
5. **이것은 기술 발표이자 진영 선점이다.** Visa·Mastercard가 "에이전트 커머스에서도 신뢰와 거래 보안이 핵심"이라며 동행을 선언했고, Shopify·Priceline·Klaviyo·Square·Intuit가 사례로 붙었다. NVIDIA도 자체 리테일 에이전틱 커머스 블루프린트를 내놓은 상태 — 에이전틱 커머스의 표준 경쟁이 본격화됐고, Anthropic은 "안전 설계도 제공"으로 플랫폼 사업자들의 채택 장벽을 없애는 수를 두고 있다.

## 1. 무엇이 공개됐나 — 발표의 골격

| 항목 | 내용 |
|---|---|
| 저장소 | [anthropics/commerce-agents](https://github.com/anthropics/commerce-agents) (Apache 2.0, 참조 구현) |
| 에이전트 | 고객용 **쇼핑 에이전트**(검색·비교·다품목 계획·개인화·카트·주문 문의) + 운영자용 **판매자 에이전트**(판매 분석·재고·가격/프로모션·캠페인 초안) |
| 실행 경로 3종 | Messages API(참조 루프) / Claude Agent SDK / Managed Agents(베타, 호스티드) |
| 수직 예시 4종 | retail(ACME), travel, telecom, entertainment — 같은 라이브러리 위에서 스토어프런트+포털 쌍으로 동작 |
| Claude Code 플러그인 | `commerce-builder` — `/scaffold-commerce-agent`, `/add-commerce-flow`, `/author-commerce-evals`, `/review-commerce-agent` |
| 배포 | Claude API, Amazon Bedrock, Microsoft Foundry, Google Cloud Vertex AI |
| 시점 | Reuters: "홀리데이 쇼핑 시즌을 앞두고" (2026-09-02 발표) |

구조가 흥미롭다. 두 역할(shopping/merchant)이 각각 core(프롬프트·도구 계약·게이트) + runtime 3종 + skills 5개로 쪼개져 있고, 공통 규칙은 `commerce-common` 한 곳에 산다. **"한 번 정의하고 세 경로에서 실행"**이 컴파일 타임 구조로 강제돼 있는 것이다. 쇼핑 에이전트의 스킬 다섯 개는 `search-discovery`, `purchase-research`, `planning-goals`, `memory-personalization`, `customer-care` — 즉 '쇼핑'을 다섯 개의 흐름으로 분해해 각각을 독립 디렉터리(SKILL.md)로 자산화했다.

또 하나 눈에 띄는 대목: 저장소는 "참조 구현이며 유지보수하지 않고 기여를 받지 않는다"고 못 박혀 있다. 지속 제품이 아니라 **'설계 논증'으로서의 코드**다. 논문 대신 돌아가는 저장소를 주는 셈이다.

## 2. 핵심 — `docs/safety.md`가 강제하는 것들

이 문서는 "코드가 강제하는 규칙 / 여전히 모델에게 요청하는 규칙 / 배포자의 소관"을 표로 나눈, 에이전트 안전 문서로는 보기 드문 정밀한 산출물이다. 핵심만 추리면:

### 2-1. 도구 호출 안쪽에서 코드가 강제하는 규칙 (모든 경로에서 성립)

- **펜싱(Fencing).** 서드파티 텍스트는 살균(불가见문자·제어문자·위조된 턴 마커·트랜스크립트 태그 제거)되고 고정 라벨 울타리로 감싸지고 길이 상한이 걸린 뒤 모델에게 간다. 프롬프트 인젝션 표면을 물리적으로 줄이는 층.
- **카트 출처(Cart provenance).** 카트 쓰기는 이 세션의 도구가 반환한 상품 id만 받는다. 옵션이 있는 상품을 id로 지목하면 쓰기가 보류되고(variant로 안내) 라인 수·수량 상한이 걸리며, 세션의 카트 쓰기는 직렬화된다.
- **결제 없음(No payment).** `StorefrontBackend`에는 주문 메서드 자체가 없다. 호스티드 체크아웃 URL은 모델의 호출 **이후에** `checkout_handoff`에서 나와 모델을 통과하지 않는다.
- **고지문(Disclosures).** 수수료·환불 정책 같은 문구는 서버가 작성한다. 모델은 본 상품을 id로 지목할 뿐.
- **UI 페이로드.** 프레젠테이션 호출은 스키마 검증 후 모든 상품·주문·지표·변경을 서버 레코드와 조인한다. 출처 없는 id는 버려지고 보고되며, 남은 것이 없으면 컴포넌트가 거부된다. 제안 칩(chip)은 살균되고 최대 4개.
- **그라운딩(Grounding).** 약관 질문, 구매 후 질문, 본 적 없는 상품 id(쇼핑), 성과 질문·미스테이징 변경 요청(판매자)은 모델이 답하기 **전에** 읽기 도구를 강제로 돌린다(Messages API는 `tool_choice`로 강제).
- **스테이징 출처 + 가드레일 + 호스트 승인.** 판매자 쓰기는 이 세션 도구가 반환한 listing/campaign id만 스테이징할 수 있고, 가드레일(변경당 항목 수, 가격 변동폭, 프로모션 깊이, 재고 크기, 캠페인 예산, 보호 필드)은 **스테이징 시와 적용 시 모두** 검사한다. `apply_change`는 호스트가 승인 마킹한 id만 통과시킨다.
- **분석 위임(Analysis delegate).** 판매 데이터 분석은 별도 위임 에이전트로 — 쿼리는 주석 없는 단일 SELECT, 결과는 행·글자·시간 상한, 실행에 wall-clock 예산, 턴당 호출 수 상한.
- **메모리.** 팩트는 키 64자·값 200자·3개 카테고리 한정. 식별자형 값은 기본 거부. 추출은 최근 교환의 사용자·어시스턴트 텍스트만 읽고(도구 결과 절대 금지) 삭제·보존기간이 모든 경로에 적용된다.
- **정체성.** 신원은 서버가 쥔다. 어떤 도구 인자도 사용자나 판매자 이름을 담지 않고, MCP 서버는 명시적 게이트웨이 설정 없으면 loopback에만 바인딩된다.

### 2-2. "여전히 모델에게 요청하는 것" — 그리고 그 함의

프롬프트가 맡은 나머지 절반: 펜스 안 텍스트는 지시가 아니라 보고 재료라는 것, 숫자·약관은 이 대화의 도구 결과에서만 인용, 쓰기는 호출 성공 후 확인, 상품은 id로 지목 등. 흥미로운 것은 Anthropic 스스로 이렇게 쓴 점이다:

> 모델이 이 규칙을 어기면 오류는 **텍스트에 국한된다**. 그 텍스트 뒤의 모든 쓰기·수치·고지문은 위 표의 검사를 통과했으므로, 실패는 정정하면 되는 오진(misstatement)이며 되돌릴 행동은 없다.

즉 프롬프트 규칙의 역할은 "지키게 하는 것"이 아니라 **"실패의 폭발 반경을 텍스트로 제한하는 것"**이다. "이 규칙들은 모델이 지시를 따르는 한에서만 성립하고, 표의 규칙은 어떤 모델에서도 성립한다" — 모델을 바꾸거나 채팅 승인을 활성화하면 이 섹션 기준으로 평가(eval)를 다시 돌리라고 명시까지 한다. 신뢰를 모델 능력이 아니라 아키텍처에 두는 선언이다.

### 2-3. 배포자의 소관 — 칼을 쥔 채 넘기는 목록

인증·크리덴셜·레이트리밋·사기·재고 규칙·결제·메모리의 개인정보 처리(열람·삭제 라우트, 계정 삭제 플로우 연동)·로그 위생(DEBUG 로그엔 카트와 주입된 팩트 전체가 담기므로 보존기간·접근통제 필요)·승인 서피스·가드레일 수치까지. 참조 구현이 멈추는 경계를 정확히 그어뒀다 — 이 목록 자체가 "에이전트를 산업에 들이는 일의 진짜 체크리스트"로 읽힌다.

## 3. 시장 — 왜 지금인가

- **Visa·Mastercard**: 에이전트 커머스에서도 신뢰·거래 보안이 핵심이며 판매자가 고객 관계와 에이전트 행동을 통제할 수 있어야 한다는 입장으로 동행. 카드사들이 에이전트 결제 표준 주도권 경쟁 중이라는 맥락과 맞닿는다.
- **Accenture 조사**: 소비자 85%가 AI 에이전트 협업에 개방적, 약 4명 중 3명은 자신을 대신 구매할 때 '가장 친한 친구'보다 개인 AI 에이전트를 더 신뢰한다고 응답.
- **도입 사례**: Priceline의 Penny(항공·호텔·렌터카 비교, Claude 추론 활용), Shopify(Catalog·UCP·Shop Sign-in으로 참조 스토어프런트 확장), Klaviyo(선호·성과 데이터 → 인사이트·캠페인), Square(판매·인력·재고 감시 + 실행 가능한 다음 단계 제안), Intuit.
- **경쟁**: NVIDIA도 [Retail Agentic Commerce 블루프린트](https://build.nvidia.com/nvidia/retail-agentic-commerce)(자율 탐색·협상·체크아웃)를 이미 내놨고, OpenAI 등도 쇼핑 에이전트 영역을 밀고 있다. "구매를 대행하는 에이전트"의 접점 표준(프로토콜)을 누가 쥐는지가 다음 전장이다.

Anthropic의 수는 정교하다. 안전 설계를 오픈소스로 풀어 **플랫폼 사업자들의 도입 장벽(신뢰·컴플라이언스)을 없애고**, 자사가 그 지배적 추론 모델의 공급자로 남는다. 카드사·SI·커머스 플랫폼을 파트너로 묶은 것도 같은 방향이다.

## 4. 우리가 가져갈 것 — 추출 가능한 설계 패턴

이 블루프린트에서 복사할 가치가 있는 것은 커머스 코드가 아니라 **신뢰 사다리의 4층 구조**다. 실제 시스템을 만지는 에이전트라면 어디에나 적용된다:

1. **출처 게이트(provenance gate)** — 쓰기 경로는 "이 세션의 도구가 반환한 id"만 받는다. 환각·인젝션으로 조작된 지시가 실제 상태를 바꿀 경로를 끊는다.
2. **스테이징 + 호스트 승인** — 채팅 텍스트는 결코 권한이 아니다. 승인은 시스템의 승인 서피스에서만.
3. **서버 작성 고지문** — 모델은 지목만, 문구·숫자는 서버가. 사용자에게 보이는 숫자의 출처를 하나로.
4. **단일 executor, 다중 런타임** — 안전 규칙을 도구 호출 안쪽 한 곳에 두면 실행 경로가 늘어도 규칙이 샌다.
5. **실패 반경의 명시** — 프롬프트 규칙의 위반은 '텍스트 오진'으로 국한시키고, 되돌릴 행동이 없게 만드는 설계. "모델이 틀려도 시스템은 안전한가"를 역방향으로 질문하는 방식이다.
