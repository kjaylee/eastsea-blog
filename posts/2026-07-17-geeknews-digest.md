### 2. 소비자 앱을 구축하고 확장하는 법 (20pts)

**요약**: Cal AI 공동창업자 제이크 카스티요는 소비자 앱의 가장 큰 병목이 제품 개발보다 유통이라고 주장하며, 4명 팀이 수백 명의 크리에이터를 운영한 방식을 공개했다. 이 팀은 팔로워 수보다 평상시 조회수, 댓글의 대화 품질, 시청자가 크리에이터를 친구처럼 느끼는지를 20초 안에 평가했고 1만 명 이상의 후보를 검토했다. 대형 크리에이터와 아주 작은 크리에이터 양쪽의 가격 왜곡을 피하고 경쟁이 덜한 중형 크리에이터를 고정 금액으로 계약해 바이럴 상승분을 브랜드가 가져갔다. 먹방·격투기처럼 제품과 표면적으로 맞아 보여도 시청자의 구매 동기가 다른 채널은 실패했고, 서로 다른 크리에이터로 같은 틈새시장을 3~5회 시험한 뒤 성과가 없으면 즉시 중단했다. 크리에이터에게는 제품 설명과 법적 금지사항만 담은 짧은 브리프를 주고 제작 방식은 맡겼으며, 계약서·일정 알림·성과 기록·재계약을 자동화했다. 그 결과 매주 약 10명의 신규 인플루언서를 계약하는 반복 가능한 유통 시스템을 만들었고, 카스티요는 기능과 디자인이 쉽게 복제되는 시대의 남은 방어력을 실행·실험·중단 속도에서 찾는다. Business Insider는 Cal AI가 2024년 출시 후 4명 창업팀으로 성장해 2년 이내 MyFitnessPal에 인수됐고, 인플루언서 마케팅을 주 성장 채널로 사용했다는 핵심 배경을 독립적으로 확인했다.

**기술적 배경**: 사용자 생성 콘텐츠는 알고리듬 노출 가능성, 유료 광고는 예측 가능한 도달, 인플루언서 계약은 이미 형성된 신뢰를 산다는 점에서 서로 다른 상품이다. Cal AI의 방식은 광고 소재를 중앙에서 정교하게 통제하는 전통적 캠페인 대신, 적합성 선별과 운영 자동화에 투자해 많은 독립 실험을 병렬화한다. 제품 기능이 빠르게 평준화되는 2026년 소비자 앱 시장에서는 개발 속도만큼 배포 학습 속도가 경쟁력이 된다는 사례다.

**영향 분석**: 개발자와 인디 빌더는 “완성 후 마케팅”을 버리고, 기능 개발과 동시에 크리에이터 틈새시장 실험을 설계해야 한다. 스타트업은 팔로워 수나 단일 바이럴 영상 대신 기준 조회수·댓글 품질·전환율·재계약률을 운영 지표로 삼을 수 있다. 다만 Cal AI의 건강·피트니스 적합성을 게임이나 생산성 앱에 그대로 복제하면 실패할 수 있으며, 각 제품에서 콘텐츠가 자연스럽게 반복되는 장면을 먼저 찾아야 한다.

**Master 액션 포인트**:

### 3. Grok Build가 오픈 소스로 공개됨 (10pts)

**[원문 바로가기](https://github.com/xai-org/grok-build)**

**요약**: SpaceXAI가 터미널형 코딩 에이전트 Grok Build의 러스트 소스와 터미널 사용자 인터페이스, 에이전트 런타임을 아파치 2.0으로 공개했다. 공개 범위에는 문맥 조립과 모델 응답 파싱, 도구 호출을 담당하는 에이전트 루프, 코드 읽기·편집·검색·명령 실행 도구, 계획 검토·인라인 차이를 보여주는 터미널 화면이 포함된다. 스킬, 플러그인, 훅, 모델 문맥 프로토콜 서버, 서브에이전트를 적재하는 확장 계층도 들어 있어 실제 상용 에이전트 하네스를 연구할 수 있다. 대화형 화면뿐 아니라 헤드리스 스크립트/지속적 통합과 에이전트 클라이언트 프로토콜을 통한 편집기 내장도 지원한다. 공식 설명에 따르면 직접 빌드한 뒤 로컬 추론 엔진을 지정할 수 있고, 공개 저장소는 SpaceXAI 모노레포의 특정 리비전을 주기적으로 동기화한다. 다만 외부 기여를 받지 않고 공개 시점의 커밋 이력도 거의 없어, 개방형 공동개발보다 참조 구현 공개에 가깝다. 더 중요한 맥락은 공개 직전 전체 저장소가 구글 클라우드 버킷으로 업로드됐다는 개인정보 논란이 있었고 기능이 비활성화됐다는 점으로, 오픈 소스 전환만으로 과거 노출 위험이 사라지는 것은 아니다.

**기술적 배경**: 코드 생성 모델의 성능 차이가 줄면서 경쟁 지점이 문맥 조립, 도구 권한, 장기 작업 상태, 확장 시스템, 터미널 경험 같은 하네스로 이동했다. Grok Build는 약 84만 줄의 러스트로 분석됐고 Codex·OpenCode에서 포팅한 도구 구현과 고지 파일도 포함한다. 로컬 추론과 소스 감사 가능성은 폐쇄형 에이전트 대비 차별점이지만, 업로드 경로의 잔재와 방대한 코드 규모는 감사 비용 자체가 새로운 위험임을 보여준다.

**영향 분석**: 개발자는 상용 에이전트의 실제 에이전트 루프·서브에이전트 프롬프트·도구 계층을 읽고 자체 도구의 구조를 비교할 수 있다. 스타트업은 모델을 새로 훈련하지 않고도 하네스·확장·로컬 추론 계층을 차별화할 여지가 커진다. 동시에 비밀키와 전체 저장소가 에이전트의 전송 경로에 들어가는지 네트워크 수준에서 검증해야 하며, “로컬 우선”이라는 문구를 보안 증거로 간주하면 안 된다.

**Master 액션 포인트**:

1. OpenClaw의 스킬/훅/서브에이전트 적재 방식과 Grok Build의 공개 구현을 읽기 전용으로 비교해, 장기 작업 상태 복구와 인라인 차이 검토에서 가져올 수 있는 패턴만 설계 메모로 추출한다.

### 4. ChatGPT는 실제로 어떻게 출처를 고르는가 (네트워크 트래픽 분석) (13pts)

**요약**: 저자는 로그인된 ChatGPT Pro 계정의 며칠치 네트워크 트래픽에서 약 1,240개 출처 레코드를 추출해 최종 답변 뒤의 검색 파이프라인을 분석했다. 각 결과에는 `result_source`가 붙으며 관찰된 값은 일반 검색을 뜻하는 `serp`, 확립된 매체군을 다루는 `labrador`, 상용 수집 계층으로 보이는 `bright`와 `oxylabs` 네 가지였다. 질문은 `turn_use_case`로 분류되고 `text`로 처리되면 웹 검색 없이 학습 데이터만으로 답했는데, 제한된 실험에서 최신 고위험 질문도 이 경로로 들어간 사례가 있었다. 사고 모델의 비교 질문은 하나의 프롬프트를 약 15~40개의 하위 검색으로 확장하고, `site:` 검색이나 가격 추정 후 확인 같은 매우 문자적인 탐색을 수행했다. 저자는 가져옴, 인용됨, 언급됨이 서로 다른 상태이며, 동영상은 많이 가져왔지만 텍스트 근거 부족으로 인용되지 않는 반면 Reddit은 상대적으로 자주 인용됐다고 관찰했다. 출처는 도메인별로 중복 제거되므로 얇은 페이지 여러 개보다 특정 주장 하나를 명확히 뒷받침하는 강한 페이지 한 개가 유리하다는 결론이다. 다만 단일 계정과 기술·서비스형 질문에 치우친 작은 표본이므로 구조적 필드의 존재는 강한 증거지만 비율과 순위는 일반화하면 안 된다고 저자가 명시했다.

**기술적 배경**: 전통 검색 최적화는 검색 결과 순위 노출을 목표로 하지만, 생성형 답변은 먼저 질문을 분류하고 여러 검색 공급자와 하위 질의를 거친 뒤 문장 단위로 인용을 선택한다. 그래서 자바스크립트 뒤에 숨은 가격표, 이미지 속 숫자, 동영상만 있는 설명은 검색되더라도 근거로 채택되기 어렵다. Search Engine Land는 별도 연구자가 1,000개 프롬프트를 최대 10회씩 실행한 9,946건에서도 같은 내부 레이블과 파이프라인 전환을 관찰했다고 보도해, 필드 구조를 독립적으로 뒷받침했다.

**영향 분석**: 개발자는 인공지능 검색 노출을 페이지 수 경쟁이 아니라 크롤링 가능한 사실, 문장별 근거, 안정된 정적 주소의 문제로 봐야 한다. 스타트업과 인디 빌더는 공식 페이지에 가격·사양·지원 범위를 일반 HTML 텍스트로 명시하고, 평가와 추천은 독립 리뷰·커뮤니티 검증을 통해 확보해야 한다. OpenClaw의 리서치 결과도 최종 인용만 보지 말고 “실제로 검색했는가, 어느 원문을 읽었는가, 독립 출처가 있는가”를 로그로 남겨야 한다.

**Master 액션 포인트**:

2. OpenClaw 브리핑 검증기에 “최신·고위험 질문의 실제 웹 조회 여부”와 “가져옴/인용/독립 교차확인”을 분리 기록하는 필드를 추가해 비검색 답변을 자동 차단한다.

### 5. LeafWiki – 서버와 DB 없이 단일 바이너리로 실행하는 셀프 호스팅 위키 (1pts)

**[원문 바로가기](https://leafwiki.com/)**

**요약**: LeafWiki는 런북, 홈랩 문서, 팀 노트처럼 오래 유지할 자료를 폴더 트리로 관리하는 경량 셀프 호스팅 위키다. 하나의 Go 바이너리로 실행되며 Node.js·Redis·Postgres 같은 외부 런타임이나 데이터베이스 서버를 요구하지 않는다. 본문은 디스크의 일반 마크다운 파일로 남고 링크·태그·검색 색인 같은 메타데이터만 SQLite가 관리해, 앱 없이도 읽고 복사할 수 있다. 편집기는 실시간 미리보기, 자동 저장, 이미지 붙여넣기, Obsidian 호환 위키링크를 제공하고 전체 텍스트 검색과 태그 필터, 빠른 이동을 지원한다. 선택적으로 리비전 복구, 페이지 이동 시 링크 자동 갱신, 깨진 링크 탐지, Mermaid와 KaTeX 렌더링을 켤 수 있다. 비공개 위키, 공개 읽기/인증 편집, 인증 없는 로컬 메모의 세 실행 모드를 지원하며 Authentik·Authelia·Keycloak 헤더 인증과도 연결된다. 실시간 공동 편집·복잡한 승인 흐름·대규모 조직 권한은 의도적으로 범위 밖이라 Notion이나 Confluence의 완전한 대체재는 아니다.

**기술적 배경**: 기존 팀 위키는 애플리케이션 런타임과 별도 데이터베이스, 백업 절차까지 운영해야 하고, SaaS 노트는 데이터 이동성과 장기 보존이 약할 수 있다. LeafWiki는 “마크다운 원본+SQLite 메타데이터+단일 배포물”로 구조를 줄여 작은 팀과 홈랩의 운영 비용을 낮춘다. LinuxLinks의 독립 리뷰도 단일 Go 바이너리, 마크다운 디스크 저장, 트리 탐색, 전체 검색, 역할 기반 접근 제어를 확인했다.

**영향 분석**: 개발자와 인디 팀은 데이터베이스 덤프 없이 폴더 복사만으로 백업 가능한 내부 런북을 빠르게 마련할 수 있다. OpenClaw처럼 마크다운을 직접 다루는 에이전트는 별도 내보내기 없이 같은 원본을 검색·편집할 수 있어 자동화 친화적이다. 다만 동시 편집과 세밀한 권한이 필요한 팀, 외부 공개 문서의 고가용성이 필요한 서비스에는 기능과 운영 성숙도를 먼저 검증해야 한다.

**Master 액션 포인트**:

1. 기존 `memory/*.md`를 복제한 비운영 데이터로 LeafWiki를 NAS에 시험 배치해 검색 속도, 위키링크, 모바일 열람, 백업 복구를 검증한다.
2. 원본 마크다운 소유권은 현재 저장소에 유지하고 LeafWiki는 보기·편집 계층으로만 평가해, 도구 잠금이나 동시 편집 충돌이 확인되면 즉시 제거할 수 있게 한다.

### 6. [이해가 새로운 병목이다](https://www.geoffreylitt.com/2026/07/02/understanding-is-the-new-bottleneck.html) (52pts)

**[원문 바로가기](https://www.geoffreylitt.com/2026/07/02/understanding-is-the-new-bottleneck.html)**

**요약**: AI 에이전트가 코드를 만드는 속도가 사람이 시스템을 이해하는 속도를 앞지르면서, 코드 생성보다 인간의 이해가 개발의 새 병목이 됐다는 주장이다. 저자는 이해의 목적을 단순히 결과를 승인하거나 거부하는 검증이 아니라, 다음 아이디어를 제안하고 여러 번의 작업 루프에 창의적으로 참여하는 능력으로 본다. 원시 코드 차이만 읽는 대신 기존 시스템의 배경, 변경 목표, 직관적 설명, 실행 순서로 재구성한 ‘서술형 코드 설명서’를 먼저 읽으라고 권한다. 설명서 끝의 퀴즈는 실제 이해 여부를 확인하는 속도 조절 장치이며, 저자는 퀴즈를 통과하기 전에는 코드를 다른 사람에게 보내지 않는 규칙을 쓴다. 또 에이전트에게 내부 상태를 직접 조작할 수 있는 디버거·시뮬레이션 같은 ‘마이크로월드’를 만들게 하면 손으로 전체를 구현하지 않고도 시스템 감각을 얻을 수 있다고 설명한다. 결론은 사람을 루프에서 제거하는 자동화가 아니라, AI를 이용해 사람이 더 깊이 루프에 들어가도록 증강해야 한다는 것이다.

**기술적 배경**: 에이전트 코딩은 패치 생성과 자체 테스트를 빠르게 만들었지만, 반복 변경의 의도와 구조가 사람의 머릿속에 남지 않으면 ‘인지 부채’가 쌓인다. 2026년의 별도 연구도 207명 학생의 회고 일지 621건에서 블랙박스 수용, 맥락 불일치, 의존성에 따른 역량 퇴화, 검증 생략을 이해 부채의 축적 패턴으로 분류했고, 반대로 AI를 이해를 돕는 비계로 쓸 때 이를 완화할 수 있다고 보고했다. 기존 대안인 전 파일 차이 검토나 테스트 통과 여부만으로는 ‘현재 변경의 정답성’은 확인해도 다음 변경을 설계할 정신 모형까지 만들기 어렵다는 점이 차별점이다.

**영향 분석**: 개발자는 산출 코드량보다 변경의 의도와 시스템 경계를 설명할 수 있는지가 핵심 역량이 된다. 스타트업은 에이전트 덕분에 구현 속도가 빨라져도 리뷰·온보딩·장애 대응에 필요한 공유 이해가 따라오지 않으면 유지보수 비용이 더 빨리 증가할 수 있다. 인디 빌더에게는 혼자 여러 에이전트를 돌릴수록 ‘왜 이렇게 됐는지 모르는 작동 코드’가 누적되는 위험이 특히 크다.

**Master 액션 포인트**:

1. OpenClaw의 구현 완료 게이트에 `변경 배경 → 핵심 데이터 흐름 → 실패 경로 → 5문항 이해 확인`을 담은 짧은 설명 산출물을 추가하고, 핵심 질문에 답하지 못하면 병합하지 않는다.
2. 게임 파이프라인의 복잡한 런타임 변경에는 디버그 HUD나 재생 가능한 상태 시각화 한 개를 함께 만들게 해, 코드만 읽지 않고 실제 상태 변화를 조작하며 검증한다.

### 7. [이봐, 신입, 우린 당신에게 주어진 일이나 끝내라고 채용한 게 아니야](https://newsletter.kentbeck.com/p/hey-n00b-we-didnt-hire-you-to-complete) (38pts)

**[원문 바로가기](https://newsletter.kentbeck.com/p/hey-n00b-we-didnt-hire-you-to-complete)**

**요약**: Kent Beck은 신입 엔지니어의 가치를 완료한 티켓 수가 아니라 앞으로 주변 사람의 생산성까지 높일 가능성으로 평가해야 한다고 말한다. 선임 입장에서 신입은 조직을 크게 바꾸는 A, 안정적으로 성장하는 B, 오래 남기 어려운 C로 나뉘며 신입은 행동으로 자신이 어느 쪽인지 신호를 보낸다. B의 기본 신호는 코드가 실제로 동작하고, 진행 상황을 공유하며, 합리적인 시간 안에 끝내고, 리뷰어·온콜·운영 담당자에게 불필요한 후속 일을 만들지 않는 것이다. A는 작업을 더 많이 닫는 사람이 아니라 불필요한 일을 제거하고, 효과가 큰 10%를 찾고, 여러 구현을 비교하며, 작은 변경을 연속 제출하고, 배운 것을 도구나 문서로 확산하는 사람이다. 이런 행동은 단순 완료보다 시간이 더 들지만, 생산성의 현재값보다 학습과 영향력의 증가율을 보여준다. 다만 끝없는 곁가지 작업을 허용하는 것은 아니며, 맡은 일을 합리적인 시간 안에 끝낸 뒤 절약한 시간을 자신과 동료의 미래 생산성에 재투자해야 한다.

**기술적 배경**: 티켓 수, 커밋 수, 코드 줄 수 같은 활동 지표는 관측하기 쉽지만 영향·품질·협업·학습을 놓쳐 굿하트의 법칙에 취약하다. Microsoft Research와 GitHub 연구진의 SPACE 프레임워크도 개발자 생산성을 단일 활동 수치로 측정할 수 없고 만족·성과·활동·소통·효율의 여러 차원으로 봐야 한다고 정리한다. Beck의 글은 이 조직 차원의 프레임을 신입의 행동 신호로 번역해, 단기 처리량 대신 학습 속도와 주변 사람에게 남기는 레버리지를 강조한다.

**영향 분석**: 개발자는 ‘완료했습니다’보다 동작 증거, 작은 변경, 학습 기록, 재사용 도구를 함께 남길수록 평가 가능한 신뢰를 만든다. 스타트업이 단기 티켓 처리량만 압박하면 신입이 설계 개선·문서화·테스트를 포기해 미래 생산성을 깎을 수 있다. 혼자 일하는 인디 빌더에게도 기능 개수보다 반복 가능한 파이프라인과 시장 학습을 남겼는지가 더 좋은 성과 지표다.

**Master 액션 포인트**:

1. OpenClaw 서브에이전트 완료 보고를 `동작 증거 / 제거한 불필요 작업 / 재사용 가능한 학습` 세 칸으로 평가해, 단순 파일 수나 토큰량이 성과 지표가 되지 않게 한다.
2. 게임 팩토리 주간 지표에 출시 개수와 함께 `자동화 재사용 횟수`, `회귀 테스트 추가`, `플레이테스트에서 폐기한 가설`을 기록한다.

### 14. SQLite에도 Rust 스타일의 에디션이 필요함 (6pts)

**[원문 바로가기](https://mort.coffee/home/sqlite-editions/)**

**요약**: SQLite는 임베디드 데이터베이스의 사실상 표준이지만, 오랜 하위 호환성 약속 때문에 오늘날 기준으로 위험하거나 느린 기본값을 유지한다는 문제 제기다. 대표적으로 외래 키 검사가 기본 비활성화되어 있어 참조 무결성이 깨질 수 있고, 재사용된 `ROWID` 때문에 끊어진 참조가 엉뚱한 새 행을 가리킬 가능성도 있다. 일반 테이블은 타입 친화성만 적용하므로 선언된 타입과 다른 값도 저장할 수 있으며, 이를 막는 `STRICT`는 테이블마다 따로 지정해야 한다. 동시 쓰기에서는 기본 대기 없이 `SQLITE_BUSY`가 발생할 수 있어 `busy_timeout` 같은 설정을 애플리케이션이 직접 챙겨야 한다. 성능 측면에서도 WAL이 기본 비활성화되어 있고 서버형 운용에 유용한 `synchronous=NORMAL` 역시 명시적으로 켜야 한다. 글은 이 설정들을 `PRAGMA edition = 2026` 같은 연도 기반 묶음으로 제공해 기존 프로그램은 깨지지 않게 두면서 신규 프로그램만 현대적 기본값을 선택하게 하자고 제안한다.

**기술적 배경**: Rust 에디션은 언어와 컴파일러를 갈라놓지 않고도 프로젝트 단위로 새 기본 동작을 선택하게 한다. SQLite에도 같은 방식을 적용하면 `foreign_keys=ON`, `busy_timeout`, WAL, 엄격 테이블 같은 안전·성능 설정을 한 번에 버전 고정할 수 있다. SQLite 공식 문서도 외래 키가 기본 비활성화되어 있고 `STRICT`가 테이블별 기능임을 확인해 주므로 문제 진단 자체는 타당하다. 다만 에디션이 모든 워크로드에 맞는 만능 설정은 아니며, WAL과 동기화 수준은 파일 시스템·내구성 요구·다중 프로세스 구조에 따라 벤치마크가 필요하다.

**영향 분석**: 개발자는 SQLite 초기화 코드에 흩어진 프라그마를 공통 부트스트랩으로 모으고, 연결마다 실제 적용 여부를 검증해야 한다. 스타트업과 인디 빌더에게는 별도 데이터베이스 서버 없이도 안전한 로컬 우선 제품을 만들 수 있다는 장점이 있지만, “SQLite는 설치 없이 바로 안전하다”는 가정은 데이터 손상과 간헐적 잠금 오류로 되돌아올 수 있다. 에디션이 실제 도입되기 전까지는 애플리케이션 차원의 명시적 프로파일이 현실적인 대안이다.

**Master 액션 포인트**:

- OpenClaw와 게임 파이프라인에서 생성하는 모든 SQLite 상태 데이터베이스의 연결 초기화 코드를 찾아 `foreign_keys`, `busy_timeout`, 저널 모드, 동기화 수준을 한 곳에서 선언하고 시작 시 `PRAGMA` 조회로 검증한다.
- 신규 로컬 저장소에는 `STRICT` 테이블을 기본 템플릿으로 쓰되, 기존 데이터베이스는 마이그레이션 호환성 테스트 뒤에만 전환한다.

**영향 분석**: 개발자에게 프롬프트 엔지니어링보다 하네스 엔지니어링과 평가 인프라의 중요성이 커진다. 스타트업은 모델 교체만으로 차별화하기 어렵고 실제 사용자 실패가 축적된 정책 코드와 회귀 평가가 장기 자산이 된다. 인디 빌더도 소규모 훅 몇 개로 검수 시간을 크게 줄일 수 있지만, 판단형 품질까지 억지로 규칙화하면 제품 유연성이 사라진다.

**Master 액션 포인트**:

- OpenClaw의 절대 금지 규칙 가운데 셸 대상 경로, 브라우저 노드, 외부 발신, 발행 전 검증처럼 기계 판정 가능한 항목을 문서 지시에서 사전 실행 훅으로 옮기고 차단 회귀 테스트를 만든다.
- `briefing-validator.sh`처럼 이미 효과가 검증된 가드를 공통 실행 계층으로 승격하고, 실패 로그를 다음 훅 후보를 찾는 데이터로 누적한다.

## 오늘의 트렌드 종합

- **메가 트렌드**: 첫째, 프론티어 모델 경쟁이 폐쇄형 API의 성능 순위에서 오픈 웨이트·오픈 하네스·긴 문맥·맞춤 학습으로 확장되고 있다. 둘째, 코드와 콘텐츠 생성 비용이 내려갈수록 병목은 인간의 이해, 검증 가능한 출처, 배포 속도, 결정론적 통제로 이동한다.
- **기회 신호**: 게임 파이프라인에는 Cal AI식 크리에이터 틈새 실험과 RGB Gaslighter식 30초 공유 루프를 결합할 여지가 있다. OpenClaw에는 Grok Build의 구조를 읽기 전용으로 비교하고, Inkling·Kimi K3를 기존 모델과 동일한 20개 고정 과제로 비용·성공률·지연을 평가할 기회가 있다.
- **위험 신호**: 오픈 소스라는 이름이 개인정보·원격 업로드·공급자 벤치마크 위험을 자동으로 없애지 않는다. X처럼 원문 접근이 제한되거나 ChatGPT가 최신 질문을 검색 없이 처리하는 경우도 있어, 실제 조회 여부와 독립 교차확인을 발행 게이트로 유지해야 한다.
- **시나리오**: 최선은 하네스와 유통 실험이 복리 자산이 되는 경우, 기준은 새 도구를 격리 평가해 일부만 흡수하는 경우, 최악은 모델 데모를 검증 없이 운영 저장소와 제품에 연결해 비용·비밀·인지 부채를 함께 키우는 경우다.
