# D1 단일 원장 전환 조사

## 현재 상태

- 공개 D1 API는 게시물 1,550건을 반환한다.
- 정적 `posts.json`은 1,338건으로 D1보다 212건 적다.
- 정적 `sitemap.xml`은 게시물 URL 490건만 포함한다.
- 홈페이지는 D1을 페이지 단위로 읽지만 `MAX_POSTS = 500`에서 강제로 중단한다.
- 개별 글 화면은 D1을 우선하고, 사이드바 장애 시 `posts.json`을 사용한다.
- 발행 도구는 마크다운과 D1을 함께 갱신하므로 실패 지점에 따라 복제본이 어긋날 수 있다.

## 선택지

1. 정적 파일을 다시 원장으로 삼는다.
   - 장점: 호스팅이 단순하다.
   - 단점: 이미 드리프트했고 검색·전체 목록을 매번 재배포해야 한다.
2. D1만 남기고 모든 정적 복제본을 삭제한다.
   - 장점: 원장이 명확하다.
   - 단점: API 장애 시 복구 경로와 기존 테스트가 동시에 사라진다.
3. D1을 유일한 서비스 원장으로 정하고 정적 파일은 배포 시 생성되는 읽기 전용 투영으로 취급한다.
   - 장점: 서비스 일관성과 정적 복구 경로를 함께 보존한다.
   - 단점: 배포 단계에서 D1 조회가 실패하면 배포도 중단해야 한다.

## 결정

선택지 3을 채택한다. 홈페이지와 개별 글은 D1을 직접 읽고, `posts.json`, 사이트맵, 피드는 D1에서 배포 스테이지로 생성한다. Git의 마크다운은 작성·감사·재해 복구 자산이며 공개 목록의 원장이 아니다.

## 구현 경계

- 홈페이지 500건 제한을 제거하고 API의 `total`을 종료 조건으로 사용한다.
- 배포 스테이지에서 D1 전체 목록을 읽어 `posts.json`, `sitemap.xml`, `rss.xml`, `atom.xml`, `feed.xml`을 생성한다.
- 기존 사이트맵의 비게시물 URL은 보존한다.
- D1 조회나 데이터 검증이 실패하면 생성 및 배포를 실패 종료한다.
- 신규 외부 의존성은 추가하지 않는다.
